## Задание

**«Разработка защищенного REST API с интеграцией в CI/CD»**

**Назначение:** получить практический опыт разработки безопасного backend-приложения с автоматизированной проверкой кода
на уязвимости. Освоить принципы защиты от OWASP Top 10 и интеграцию инструментов безопасности в процесс разработки.

Выполните следующие шаги для создания простого, но защищенного веб-API:

#### 1. Выбор стека и инициализация проекта:

- Выберите язык программирования (`Python/Flask`, `JavaScript/Node.js` + `Express`, `Java`).
- Создайте новый проект с помощью менеджера пакетов (`npm`, `pip`, `maven`).
- Инициализируйте `git`-репозиторий и свяжите его с удаленным репозиторием на `GitHub` или `GitLab`.

#### 2. Разработка функционального API:

- Реализуйте 3 метода:
    1) POST /auth/login — метод для аутентификации пользователя (принимает логин и пароль).
    2) GET /api/data — метод для получения каких-либо данных (например, список пользователей или постов). Доступ должен
       быть только у аутентифицированных пользователей.
    3) Придумайте сами
- Для хранения данных используйте любую удобную базу данных (SQLite для простоты или PostgreSQL) или даже простой
  файл/массив в памяти, если это учебный пример.

#### 3. Внедрение базовых мер защиты:

- Защита от `SQLi` (SQL-инъекций): Используйте параметризованные запросы (Prepared Statements) или `ORM` (например,
  `Sequelize`, `SQLAlchemy`, `Hibernate`). Не используйте конкатенацию строк для формирования `SQL`-запросов.
- Защита от `XSS`: Санитизируйте (экранируйте) все пользовательские данные, которые возвращаются в ответах API.
  Используйте встроенные функции фреймворка (например, `escape()` в `Express`).
- Защита от `Broken Authentication`:
    - Реализуйте выдачу `JWT`-токена upon successful login.
    - Напишите middleware, которое будет проверять `JWT`-токен на всех защищенных эндпоинтах.
    - Пароли ни в коем случае не должны храниться в открытом виде. Обязательно хэшируйте их с помощью алгоритмов типа
      `bcrypt`, `scrypt` или `Argon2`.

#### 4. Настройка CI/CD pipeline с security-сканерами:

- В корне проекта создайте конфигурационный файл для GitHub Actions (`.github/workflows/ci.yml`) или GitLab CI (
  `.gitlab-ci.yml`).
- `SAST` (Static Application Security Testing): Настройте в pipeline запуск статического анализатора кода.
    - Для `Python`: `bandit` или `safety`
    - Для `JavaScript`: `npm audit` или `snyk test`
    - Для `Java`: spotbugs или использование плагина `OWASP Dependency-Check`
- `SCA` (Software Composition Analysis): Настройте проверку зависимостей на
  известные уязвимости.
    - Используйте `OWASP Dependency-Check` или `Snyk`.
    - Настройте `step` в `pipeline`, который будет запускать сканер и выдавать отчет.
- При каждом push в репозиторий или создании pull request должны автоматически запускаться проверки.

#### 5. Тестирование и документирование:

- Протестируйте работу API с помощью `Postman` или `curl`. Убедитесь, что аутентификация работает, а доступ без токена —
  запрещен.
- Сделайте скриншоты отчетов от SAST/SCA-инструментов, которые показывают, что проверки прошли успешно (не найдено
  критических уязвимостей) или что найденные уязвимости были вами исправлены.

### Что сдают студенты

1. Ссылка на **публичный git-репозиторий** (GitHub/GitLab) с кодом проекта.
2. Текст файла README.md из репозитория, содержащий:
    - Описание проекта и API (какие эндпоинты есть, как их вызывать).
    - **Подробное описание реализованных мер защиты** (как именно защищены от `SQLi`, `XSS`, как реализована
      аутентификация).
    - Скриншоты отчетов SAST/SCA из раздела "Actions" / "CI/CD" вашего репозитория.
3. Ссылка на последний успешный запуск pipeline в вашем репозитории.

### Критерии оценки

- **3 балла:** Работоспособность API. Эндпоинты аутентификации и получения данных
  возвращают корректные ответы.
- **4 балла:** Реализация мер защиты:
    - 1 балл за защиту от SQLi.
    - 1 балл за защиту от XSS.
    - 2 балла за корректную реализацию аутентификации (JWT + хэширование паролей).
- **2 балла:** Настройка CI/CD pipeline с запуском как минимум одного SAST/SCA инструмента.
- **1 балл:** Качество оформления отчета (четкость, структурированность, наличие скриншотов), качество документации и
  оформления кода.

## Контрольные вопросы

<details>
  <summary><b>1. Почему хэширование пароля с помощью алгоритмов вроде bcrypt предпочтительнее использования SHA-256?</b></summary>

  <br>

Алгоритмы SHA-256 и bcrypt относятся к разным классам хэш-функций, и их ключевое отличие — это **цель применения**.

| Характеристика                 | **SHA-256**                                      | **bcrypt**                                  |
|:-------------------------------|:-------------------------------------------------|:--------------------------------------------|
| **Назначение**                 | Хэширование данных (файлы, подписи, сертификаты) | Хэширование паролей                         |
| **Скорость**                   | Очень высокая (специально оптимизирован)         | Намеренно медленный                         |
| **Параметр сложности**         | Отсутствует                                      | Настраиваемый «cost factor»                 |
| **Устойчивость к brute-force** | Низкая (GPU перебирает миллиарды хэшей/сек)      | Высокая (перебор кратно замедляется)        |
| **Встроенная соль**            | Отсутствует                                      | Присутствует (уникальна для каждого пароля) |

**Причины предпочтения bcrypt в случае хеширования паролей:**

1. **Намеренная медлительность.** SHA-256 оптимизирован для скорости — современные GPU способны вычислять
   сотни миллионов SHA-256-хэшей в секунду, что делает перебор паролей тривиальным. bcrypt имеет параметр `cost`,
   который
   позволяет масштабировать сложность вычисления по мере роста вычислительных мощностей, не меняя алгоритм.
2. **Встроенная соль.** bcrypt автоматически генерирует уникальную случайную соль для каждого пароля и включает её в
   итоговый хэш. Это делает бесполезными атаки с использованием заранее вычисленных таблиц (rainbow tables), так как
   одинаковые пароли у разных пользователей будут иметь разные хэши.
3. **Защита от компрометации базы данных.** Даже если злоумышленник получит базу данных с bcrypt-хэшами, взлом каждого
   отдельного пароля будет занимать значительное время из-за вычислительной сложности алгоритма.

**Вывод:** SHA-256 не предназначен для паролей. Его скорость, являющаяся достоинством при работе с файлами, становится
критическим недостатком при защите паролей. Для хэширования паролей следует использовать специализированные алгоритмы.

</details>
<details>
  <summary><b>2. В чем заключается основная разница между SAST и DAST-подходом к тестированию безопасности?</b></summary>

  <br>

**SAST** (Static Application Security Testing) и **DAST** (Dynamic Application Security Testing) — два
взаимодополняющих подхода к анализу безопасности приложений.

| Критерий                      | **SAST**                                                          | **DAST**                                                    |
|:------------------------------|:------------------------------------------------------------------|:------------------------------------------------------------|
| **Объект анализа**            | Исходный код, байт-код (white-box)                                | Работающее приложение снаружи (black-box)                   |
| **Время проведения**          | На этапе разработки, до запуска                                   | На этапе тестирования или в runtime                         |
| **Что находит**               | Уязвимости в коде: SQLi, XSS, небезопасные функции, утечки памяти | Runtime-проблемы: XSS, SQLi, CSRF, misconfiguration сервера |
| **Указывает на место в коде** | Да — точная строка и файл                                         | Нет — только факт уязвимости                                |
| **Зависимость от языка**      | Да — нужна поддержка конкретного языка/фреймворка                 | Нет — работает с любым приложением                          |
| **Ложные срабатывания**       | Высокая вероятность (false positives)                             | Ниже, т.к. уязвимость реально эксплуатируется               |

**Ключевое отличие:** SAST — это анализ кода «изнутри» без запуска приложения, нацеленный на раннее обнаружение дефектов
на этапе разработки. DAST — это имитация действий злоумышленника «снаружи» против работающей системы,
позволяющая найти проблемы, которые проявляются только в реальной среде (например, ошибки конфигурации сервера или
проблемы интеграции компонентов).

На практике оба подхода используются совместно: SAST позволяет находить и исправлять уязвимости дёшево и быстро на
ранних стадиях, а DAST подтверждает реальную эксплуатируемость проблем в уже собранном приложении.

</details>
<details>
  <summary><b>3. Опишите механизм работы JWT-токена. Какая информация в нем содержится и как сервер проверяет его подлинность?</b></summary>

  <br>

**JWT** (JSON Web Token) — стандарт для безопасной передачи информации между сторонами в виде JSON-объекта, подписанного
криптографически.

**Структура токена:**

JWT состоит из трёх частей, разделённых точками: `Header.Payload.Signature`

1. **Header (Заголовок)** — JSON-объект, закодированный в Base64Url. Содержит тип токена (`"typ": "JWT"`) и алгоритм
   подписи (`"alg": "HS256"` или `"RS256"`).
2. **Payload (Полезная нагрузка)** — JSON-объект, закодированный в Base64Url. Содержит **claims** (утверждения):
   стандартные (`sub` — идентификатор пользователя, `exp` — время истечения, `iat` — время создания) и произвольные
   пользовательские поля (например, роль пользователя). **Важно:** Payload не шифруется, а лишь кодируется — его
   содержимое может прочитать любой.
3. **Signature (Подпись)** — результат применения алгоритма подписи к строке
   `Base64Url(Header) + "." + Base64Url(Payload)` с
   использованием секретного ключа сервера.

**Механизм проверки подлинности сервером:**

1. Клиент отправляет JWT в заголовке запроса (`Authorization: Bearer <token>`).
2. Сервер **заново вычисляет** подпись из полученных Header и Payload, используя свой секретный ключ.
3. Полученная подпись сравнивается с подписью из токена: если они совпадают — токен подлинный и данные в Payload не
   изменялись.
4. Сервер проверяет поле `exp` — не истёк ли срок действия токена.

**Вывод:** Безопасность JWT строится не на секретности Payload, а на невозможности подделать подпись без знания
секретного ключа. Именно поэтому критически важно никогда не помещать в Payload чувствительные данные (пароли,
платёжную информацию) и хранить секретный ключ в надёжном месте.

</details>
<details>
  <summary><b>4. Какие риски возникают, если не проводить аудит сторонних библиотек (зависимостей) в проекте?</b></summary>

  <br>

Современные проекты зачастую содержат сотни транзитивных зависимостей (зависимости зависимостей). Каждая из них —
потенциальная точка входа для злоумышленника.

1. **Использование библиотек с известными уязвимостями (CVE).** Уязвимости в популярных библиотеках регулярно
   обнаруживаются и публикуются в открытых базах данных (NVD, CVE). Если зависимости не обновляются и не проверяются,
   приложение остаётся уязвимым к атакам, для которых уже существуют готовые эксплойты. Классический пример — уязвимость
   Log4Shell (CVE-2021-44228) в библиотеке Log4j, затронувшая тысячи продуктов по всему миру.
2. **Атаки на цепочку поставок (Supply Chain Attacks).** Злоумышленник может скомпрометировать саму библиотеку:
   взломать аккаунт мейнтейнера и опубликовать вредоносную версию пакета, или создать пакет с похожим названием
   (typosquatting). Без аудита вредоносный код попадёт в продакшн незамеченным.
3. **Использование заброшенных или неподдерживаемых пакетов.** Библиотека, которую больше не поддерживает автор, не
   получает обновлений безопасности. Новые уязвимости в ней никогда не будут закрыты патчем, и зависимость становится
   постоянной угрозой.
4. **Нарушение лицензионных требований.** Аудит зависимостей включает проверку лицензий. Некоторые лицензии (например,
   GPL) требуют открытия исходного кода всего проекта при его использовании. Незамеченное нарушение может повлечь
   юридические последствия.
5. **Чрезмерно широкие права доступа у пакетов.** Некоторые библиотеки запрашивают или получают доступ к сетевым
   соединениям, файловой системе или переменным окружения, что может быть использовано для эксфильтрации данных.

**Инструменты для аудита:** `npm audit` (Node.js), `pip-audit` (Python), `Dependabot` (GitHub), `Snyk`, `OWASP
Dependency-Check`. Регулярный аудит зависимостей — обязательная практика в рамках процесса безопасной разработки
(SDLC).

</details>
